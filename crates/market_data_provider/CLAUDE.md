# CLAUDE.md — market_data_provider

Workspace-wide rules (coding standards, commands, what goes in `layline`) are in the root `CLAUDE.md`. Paths below are relative to this crate unless they start with `layline::` or `crates/`.

## Purpose

The market data provider connects to exchanges, normalises market data, and publishes it to strategy processes over shared memory with minimal latency. Strategies subscribe to topics through the provider's local HTTP API. `BinanceConnector` publishes real BBOs and trades (spot and USDⓈ-M perpetual); `OkxConnector` is still a dummy emitting synthetic BBOs and trades every 10 ms. Candlesticks are not published, because strategies build them from trades. A provider serves either live or demo data for its whole lifetime, chosen by `demo` in its TOML config; strategy requests must ask for the same environment.

## Code layout

- This crate: the provider library (its binary is `src/bin/market_data_provider.rs` at the workspace root): `server` (HTTP, coordinator, registry, `run`/`serve`), `exchanges` (connectors, workers, router, `websocket`), `phanes_client` (API key client), `alert`, `config`, `exit_reason`, `time` (venue timestamp unit conversions), `utils` (`Clock`). Only the root binary, the integration tests and the benches use it; strategies never depend on it.
- `layline` holds the contract with strategies: `layline::types`, `layline::shared_memory` (`MarketDataReader`, `MarketDataWriter`, ring format) and `layline::provider_api` (HTTP contract), plus the Gnosis protocol, Bark, secret files and logging shared with Phanes.
- `crates/dummy_strategy` (binary `src/bin/dummy_strategy.rs` at the workspace root) reads market data through `layline` only. It owns the strategy side of the HTTP protocol (`client.rs`) and its own `Strategy` trait; when real strategies arrive, move the client into layline.

## Commands

```bash
cargo run --bin market_data_provider -- --config market_data_provider.toml   # publisher; copy deploy/market_data_provider.example.toml, chmod 600
crates/market_data_provider/deploy/market_data_provider.sh install|uninstall|reinstall [--yes]   # deploy as a systemd service on the trading host
cargo run --bin dummy_strategy -- --demo      # consumer / latency bench; must match the config's `demo`
cargo test -p market_data_provider            # unit tests + tests/subscription.rs end-to-end
cargo bench -p market_data_provider                                     # criterion latency benches
cargo bench -p market_data_provider -- --save-baseline before           # then compare with --baseline before
cargo test -p market_data_provider --bench latency                      # run each bench once as a smoke test
```

**Units:** venue timestamp unit conversions live in `src/time.rs`, which also carries the TODO to make units distinct types.

## Benchmarks

`crates/market_data_provider/benches/latency.rs` (criterion) measures the data path bottom up: `codec` (rkyv serialize, and the reader's copy plus deserialize), `publish` (`MarketDataWriter::publish` into a ring in `/dev/shm`), `poll_fan_out` (`MarketDataReader::poll` over 1/8/64 rings, idle and with one active), and `cross_thread_latency` (one-way write-to-read between two threads, ping-pong so nothing queues, measured as `LatencyMetric` reports it). The ring code is `layline::shared_memory`, so the benches use its public API directly. Exchange workers are not benched, because the synthetic feed ticks every 10 ms. Numbers on WSL2 without core pinning are for comparing versions, not absolute production latency; criterion reports means, not tail percentiles.

## Running provider and strategy

1. Start `market_data_provider --config <file>` (default `market_data_provider.toml`). It creates `/dev/shm/market_data_provider/` (`DEFAULT_ROOT_DIRECTORY`) and serves HTTP on `127.0.0.1:<port>` from the config; strategies assume 6666 (`layline::provider_api::DEFAULT_PROVIDER_ADDRESS`). It refuses to start if the address is taken or the config is invalid. `demo` in the config selects live or demo data for the whole lifetime. No exchange worker runs until a strategy subscribes.
2. Start `dummy_strategy`, in either order. It retries `/subscribe` with backoff, subscribes to BBO and Trade of Binance BTC and ETH, spot and perpetual (spot needs an SBE key from Phanes, or the provider exits), and records each message's provider, transport and parse latency in memory; every `--report-interval-seconds` (60 by default) a reporter thread logs per-topic and overall p50/p90/p99/p99.9/max in µs (internal = provider + transport), so measuring never delays the messages measured. Its `--demo` flag must match the config's `demo`, or every request is rejected with 400.
3. `curl localhost:6666/subscribed` lists every active topic, its ring path, and the strategies holding it.

## Deployment

`deploy/market_data_provider.sh install`, modelled on `crates/phanes/deploy/phanes.sh`, builds the release binary into `/usr/local/bin/market_data_provider` and runs it as the systemd unit `deploy/market_data_provider.service` under the strategies' user (journal namespace `market_data_provider`). `/etc/market_data_provider/` (chmod 700) holds the config (seeded once from `deploy/market_data_provider.example.toml`) and the provider's Gnosis client key pair, made with openssl as Phanes' README does for Osaka; both survive a redeploy, and the install prints the public key Phanes' `gnosis_service_config` needs. It enables linger for that user, because systemd-logind's default `RemoveIPC=yes` deletes a user's `/dev/shm` files when their last session ends, which would break the independent-restart invariant. The unit must not use `PrivateDevices`/`PrivateIPC`, so strategies outside it see the rings. `uninstall` removes the binary, unit, config, key, journal logs and `/dev/shm/market_data_provider`; `reinstall` therefore needs a new public key in Phanes.

## Design invariant: independent restarts

As long as the ring files exist, the provider and any strategy can stop or restart at any time without coordinating:

- When the provider restarts, running strategies keep reading their existing mappings. `subscribe`'s background thread calls `/resubscribe` every 10 s, which restores the topics, and the provider rejoins each ring at its existing producer position (`join_writer`).
- When a strategy restarts, it starts at the current producer position and receives only messages published after that point. It does not replay history or a last-value snapshot.
- One provider serves many strategies. A crashed strategy must never affect the others; its lease expiring is what releases its topics.
- Ring files are never deleted.

Any change to the transport, the file layout, or the startup and shutdown paths must preserve this.

## Architecture

- **Types (`layline::types`, one type per file):** `Instrument` = `exchange` + `base`/`quote` `Currency` + `UnderlyingType` (spot, or straight perpetual only). `Topic` = `Instrument` + `MarketDataType` (BBO/Trade) is the unit of subscription and deduplication. Each topic has its own ring at `{root}/{exchange}/{base}-{quote}-{SPOT|PERP}/{market_data_type}.dat`, and each connector maps `Instrument` to the venue symbol. `Bbo` and `Trade` carry their `Instrument`. `Subscription` (topic plus ring path) and `ConnectedApi`/`ConnectedApis` also live here, so `layline::shared_memory` and `exchanges` do not depend on the HTTP API. Prices and sizes are `rust_decimal::Decimal`, archived through the `RkyvDecimal` remote adapter, because rust_decimal has no rkyv 0.8 feature.
- **Control API (`layline::provider_api`):** JSON over HTTP on localhost. `/health`, `/info` (server time in UTC to the millisecond, version, build profile, lease), `/subscribed`, `/connected_apis` (GET); `/subscribe`, `/resubscribe`, `/unsubscribe` (POST, body `{strategy_name, demo, topics}`; `demo` is required and must equal the config's `demo`, or the request is rejected with 400 before any state changes). Topics nest as exchange → instrument → market data type, spelled as in ring paths: `{"Binance": {"BTC-USDT-SPOT": ["BBO", "TRADE"]}}`; responses use the same tree with a value per type (`{"Ok": path}` / `{"Err": reason}`, or `{path, strategy_names}` for `/subscribed`). In Rust a request carries `HashSet<Topic>`, a response `HashMap<Topic, SubscriptionResult>` (`SubscriptionResult = Result<PathBuf, String>`) and `/subscribed` `HashMap<Topic, TopicStatus>`; the `topic_set` / `topic_map` serde adapters in `provider_api.rs` do the nesting, and the module doc shows full examples. `/resubscribe` replaces the strategy's whole set. `/connected_apis` returns, per exchange, the venue APIs its connector calls (`[{description, api, doc}]`), so a production agent can watch venue changelogs; each connector hardcodes them in `ExchangeConnector::CONNECTED_APIS`, edited by hand whenever it starts or stops calling a venue API.
- **Server (`src/server/`):** `http` is axum. `Coordinator` sits behind one `tokio::sync::Mutex`, so requests are serialised and deduplication needs no finer locking. It owns `SubscriptionRegistry`, which reference-counts topics by strategy name. Each request renews the strategy's lease (`lease_duration`, 30 s by default); a sweep every second drops expired strategies. A topic is unsubscribed from its exchange once no strategy holds it. The provider serves one environment for its whole lifetime, chosen by the config's `demo`, so topics stay keyed by `Topic` alone: every worker starts in that environment, and every request's `demo` must match it. `/subscribe` and `/unsubscribe` log the strategy and its topics at info on arrival; `/resubscribe` logs nothing when the requested set equals what the strategy holds (order and duplicates ignored) and otherwise warns with the added and dropped topics. `exchanges::ExchangeRouter` keeps a `HashMap<Exchange, WorkerHandle>`, groups a `HashSet<Topic>` by exchange, calls the workers concurrently, and merges their `HashMap<Topic, String>` failure replies; storage lives in the coordinator's registry, and ring paths are derived from `Topic` and the root directory.
- **Exchange workers (`src/exchanges/`):** bcast `Writer` is `!Send`, so each exchange runs on its own thread with a current-thread tokio runtime. That thread owns the `ExchangeConnector` and every `MarketDataWriter` of that exchange, which guarantees a single writer per ring. Subscribe and unsubscribe take a `HashSet<Topic>` (so does `ExchangeConnector`) and return a reason per failed topic; a subscribe resolves only after the ring file exists, so the derived path is immediately readable. Workers start on demand: the first topic of an exchange spawns its worker, and the router's per-exchange arm builds the connector on the worker thread with its `new(demo, ...)`, which injects production dependencies and connects nothing (the connector picks the venue's demo or live domains); venue connections open in `subscribe`, which reports their failures. `ExchangeConnector` has no constructor, so it is implemented over the connector's generic dependencies and tests drive the same trait methods with mocks. Only spawning the thread or runtime can fail a worker start (that batch is rejected, and the next subscribe retries), and a stopped worker is replaced. A worker exits on its own after its last topic, which closes the command channel; the router therefore keeps no remaining-topic count. On shutdown the worker calls `ExchangeConnector::disconnect` to close venue connections gracefully. To add an exchange: add an `Exchange` variant, a connector module, and an arm in both `router::spawn_exchange_worker` and `exchanges::connected_apis` (both matches are exhaustive, so the compiler enforces it). `synthetic.rs` is temporary and will be deleted.
- **Transport (`layline::shared_memory`):** `bcast::RingBuffer` over `memmap2`, with a 64 KiB ring per topic. Strategies use `MarketDataReader`; only exchange workers may create a `MarketDataWriter`, so each ring keeps a single writer. `ring_format` defines the file length and the metadata area (magic, `FORMAT_VERSION`, market data type) both use; its module doc has an ASCII diagram of the whole file layout. The writer rejoins only a ring with matching metadata and otherwise resets it; readers refuse a mismatch. `bcast::mmap::MappedWriter::new` is deliberately not used, because it deletes the file. `MarketDataReader` polls every subscribed ring in turn and hands each `MarketData` with its receive time to a caller closure. On `Overrun`, it calls `reader.reset()` and skips to the latest data.
- **Strategy client (`dummy_strategy/src/client.rs`):** `subscribe` blocks until every topic is accepted (failing if any is rejected), then leaves a detached thread that resubscribes every 10 s to keep the lease and survive provider restarts.
- **Serialization:** messages are `rkyv`-encoded and copied into a 16-byte-aligned 512-byte stack buffer before `from_bytes`. Any message type must therefore serialize to at most 512 bytes. Changing `Bbo` or `Trade` changes the wire format. Nothing is deployed yet, so keep `FORMAT_VERSION` at 1 during development; bump it only after the first deployment.
- **Timestamps:** `Bbo` and `Trade` carry a `LatencyMetric`, all from `get_current_timestamp_nanoseconds()`. The connector sets `provider_receive_time_nanoseconds` via `LatencyMetric::received` as soon as it reads the venue message, before parsing. `MarketDataWriter::publish` overwrites `provider_write_time_nanoseconds` just before serialization, so serialization and the ring copy count as transport. Strategies stamp their own receive time when reading; comparing clocks requires the same host and clock source. `exchange_time_nanoseconds` is the venue's timestamp and stays outside `LatencyMetric`.
- **Venue websockets (`exchanges/websocket/`, `exchanges/binance/`):** `websocket/` is venue-agnostic. `client.rs` is the seam: one `WebSocketClient` trait, one connection per client (tungstenite in production, a mock in tests). `WebSocketConnection<Client>` owns a client for good and adds heartbeat, keepalive and close logic: `next_message` hands back only Text/Binary `Message`s and an error once the connection is gone; it answers Ping and Close explicitly, and pings and gives up per `Heartbeat`, tracked as absolute tokio instants so it stays cancel-safe. `Heartbeat` also carries `connect_timeout` (a hung handshake cannot hold the control plane) and `Keepalive`: `PingFrame` for Binance, `Text { ping, pong }` for venues such as OKX that keep alive in application text. `endpoint_set.rs` adds `EndpointSet<COUNT, Endpoint, Client>`/`EndpointState`: one connection per endpoint plus its topics-by-venue-key and restore plan, with `record_topics`, `forget_topics`, `schedule_restore` (exponential backoff), `schedule_immediate_restore` and `due_endpoints`; the next venue reuses it instead of copying Binance's bookkeeping. `venue_stream::endpoint_for_topic` maps spot to SBE (`@bestBidAsk`, `@trade`) and perpetuals to JSON futures `/public` (`@bookTicker`, `@trade`), since Binance offers SBE for spot only. SBE `bestBidAsk` may drop outdated updates under load (auto-culling), unlike JSON `bookTicker`; it arrives no earlier but decodes ~4× cheaper, and the BBO is consumed as a latest value; Binance accepts unknown stream names silently, so keep that mapping under test. `BinanceConnector` owns one `WebSocketConnection` per endpoint, keyed by stream name (`venue_stream::stream_name`, e.g. `btcusdt@bookTicker`). `endpoint.rs` holds only hardcoded API facts (URLs, docs, `CONNECTED_APIS`); topic-to-stream mapping lives in `venue_stream.rs`, until an InstrumentManager owns venue spellings. An endpoint connects on its first stream and closes with its last; each batch sends one SUBSCRIBE or UNSUBSCRIBE per endpoint and waits for its `{"result":null,"id":N}` (10 s), queueing events that arrive meanwhile; a failure fails the batch and rolls back. A lost connection, or one whose request failed, is restored inside `next_event` by reconnecting and resubscribing every stream, at once then with backoff from 1 s doubling to 60 s; the fifth failure in a row alerts the phone. `message.rs` is the single frame classifier: `classify_text_frame` returns `Response`, `Event` or `ServerShutdown`, and `handle_frame` queues data, answers a request or forces an immediate reconnect. Events take a hand-written single-pass scanner for Binance's compact layout (~150–200 ns a frame in release, against ~450 ns for serde_json), and anything it does not recognise falls back to serde_json; futures `bookTicker` and `trade` carry `T` in ms, and fills other than `X: MARKET` are skipped. `sbe.rs` decodes spot SBE `bestBidAsk` (template 10001) and trade (10000, one `Trade` per fill) frames without allocating; exchange times are in µs. The per-message path allocates nothing beyond the venue frame itself: endpoints sit in an array indexed by `BinanceEndpoint::index`, `next_event` selects over them with a fixed `select!`, and SBE stream names are built on the stack. Unknown or unparseable frames are logged and dropped, never fatal. Router, worker and integration tests use OKX, because they spawn the production Binance connector.
- **Config, API keys and alerts (`config.rs`, `phanes_client.rs`, `alert.rs`, `exit_reason.rs`; `layline::bark`, `layline::secrets`, `layline::gnosis`):** like Phanes, all config comes from one TOML file (chmod 600), never environment variables: `port`, `demo`, `[phanes]` (`url`, `gnosis_private_key_file` chmod 600, `gnosis_public_key`) and `[bark]` (see `deploy/market_data_provider.example.toml`). `layline::secrets` enforces chmod 600 for the config and Phanes keys. `ProviderConfig::load` checks everything at startup: `[phanes]` is always required and its keys are read and decoded then; `[bark]` is required by release builds only, since `layline::bark::Notifier` pushes through Bark in release builds and only logs in debug builds. `serve` hands `PhanesClient` and `Notifier` to the router as a `ConnectorContext`, which it passes to each connector's `new`. Only an endpoint that needs a key (Binance SBE) asks Phanes Gnosis for one, once per connector, via `fetch_api_key_or_panic(ApiKeySource, SendAlert, key_id)`; Phanes key ids are `binance_sbe_{real,demo}`. A failure alerts the phone with the key id and panics with an `ExitReason::ApiKeyUnavailable` payload. Exit codes count up from 1 in `ExitReason`: 1 API key unavailable, 2 any other fatal error (bad config, port taken), 3 any other panic; the binary's panic hook (`src/bin/market_data_provider.rs` at the workspace root) flushes logs and exits with the payload's code on a panic from any thread. `SendAlert` is the best-effort alert this crate implements on `Notifier`: a failed push is logged, not returned.
- **Testing without venues, Phanes or wall time:** `BinanceConnector<WebSocket, KeySource, Alerter, TimeSource>` defaults to production types; `new` takes a `create_websocket` closure per endpoint, and tests build it through `BinanceFixture` with a `websocket::tests::MockVenue` per endpoint (each connection its client opens is a channel pair the test drives, records URL and header, can refuse or ignore Close, and `respond_with` answers requests automatically; `BinanceFixture` acknowledges every request), `phanes_client::tests::MockApiKeySource` (grants or denies by key id, records requests, can go offline; no Gnosis involved), `alert::tests::RecordingAlert` and `utils::tests::MockClock`. `PhanesClient` itself is tested through `PhanesFixture`, whose mock `GnosisHttp` answers with `layline::gnosis::Responder`, the real server half of the protocol. Test-only code lives in each module's `mod tests`; fixtures shared across crates live in `layline::testing` (`instrument`, `topic`, `subscription`, `bbo`, `trade`, `test_keypair`). `tests/module_dependencies.rs` guards the import DAG. `utils::Clock` (`RealClock`, `MockClock` in tests) is for wall-clock timestamps such as `provider_receive_time_nanoseconds` and the Gnosis request time; timers use tokio time, which tests pause with `#[tokio::test(start_paused = true)]` (dev-dependency feature `test-util`), stepping just before and past each deadline. Only `websocket/client.rs` tests a real local socket; `live_futures_endpoints_deliver_bbo_and_trades` is `#[ignore]` and reaches Binance live and demo.
- **Not yet implemented (see `tmp/architecture_design.md`, a local untracked note):** an InstrumentManager that owns venue symbol spellings and trading rules, Coindesk mapped/unmapped checks, persisting the subscription set across provider restarts (resubscribing clients currently restore it), and a seqlock latest-value slot for BBO.
