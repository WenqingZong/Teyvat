# 行情服务 MarketDataProvider

连接交易所，标准化行情，以尽量低的延迟经共享内存发布给策略进程，部署在 **Osaka**。代码在 `crates/market_data_provider`（库），二进制是 `src/bin/market_data_provider.rs`。部署步骤见 [`deploy/README.md`](../deploy/README.md)，尚未实现的部分见 [`plan/market_data_provider.md`](../plan/market_data_provider.md)。

策略通过行情服务在本机的 HTTP API 订阅 topic。`BinanceConnector` 发布真实的 BBO 和逐笔成交（现货和 U 本位永续）；`OkxConnector` 目前还是 dummy，每 10 ms 发出合成的 BBO 和成交。不发布 K 线，策略自己用成交合成。一个行情服务在整个生命周期内只提供实盘或 demo 其中一种行情，由 TOML 配置里的 `demo` 决定；策略的请求必须指定同一种环境。

## 代码分布

- **本 crate**：`server`（HTTP、coordinator、registry、`run`/`serve`）、`exchanges`（connector、worker、router、`websocket`）、`phanes_client`（API Key 客户端）、`alert`、`config`、`exit_reason`、`time`（交易所时间戳的单位换算）、`utils`（`Clock`）。只有根目录的二进制、集成测试和 benches 使用它；策略从不依赖它。
- **layline** 存放和策略之间的契约：`layline::types`、`layline::shared_memory`（`MarketDataReader`、`MarketDataWriter`、ring 格式）和 `layline::provider_api`（HTTP 契约），以及和 Phanes 共用的 Gnosis 协议、Bark、密钥文件、日志。
- **单位**：交易所时间戳的单位换算在 `src/time.rs`，那里也有把单位做成独立类型的 TODO。

## 设计不变量：可以各自独立重启

只要 ring 文件还在，行情服务和任何策略都可以随时停止或重启，彼此不需要协调：

- 行情服务重启时，正在运行的策略继续读原有的映射。`subscribe` 的后台线程每 10 秒调用一次 `/resubscribe`，恢复它的 topic；行情服务在每个 ring 现有的生产者位置重新接上（`join_writer`）。
- 策略重启时，用同一个策略名重新接上自己的 ring，从当前生产者位置开始读，只收到之后发布的消息，不回放历史，也没有最新值快照。
- 一个行情服务服务多个策略。某个策略崩溃绝不能影响其他策略；它的租约过期后，它占用的 topic 才被释放。
- ring 文件永不删除。

任何对传输、文件布局、启动和关闭流程的修改，都必须保持这一点。

## 架构

- **类型（`layline::types`，一个类型一个文件）**：`Instrument` = `exchange` + `base`/`quote` `Currency` + `UnderlyingType`（现货，或普通永续）。`Topic` = `Instrument` + `MarketDataType`（BBO/Trade），是订阅和去重的单位。每个策略有自己的 ring：一个策略订阅的、同一交易所、同一品种（现货/永续）、同一行情类型的 topic 共用一个 ring，由策略名和 `RingKey`（`Topic::ring_key`）确定，路径为 `{root}/{strategy_name}/{exchange}/{SPOT|PERP}/{market_data_type}.dat`（只在 `RingKey::file_path` 里定义）；每个 connector 负责把 `Instrument` 映射成交易所的 symbol。`Bbo` 和 `Trade` 自带 `Instrument`。`StrategyName`（`String` 的类型别名，凡是表示策略名的地方都用它）、`Subscription`（topic 加 ring 路径）和 `ConnectedApi`/`ConnectedApis` 也在这里，所以 `layline::shared_memory` 和 `exchanges` 不依赖 HTTP API。价格和数量是 `rust_decimal::Decimal`，经 `RkyvDecimal` remote adapter 归档，因为 rust_decimal 没有 rkyv 0.8 的 feature。
- **控制 API（`layline::provider_api`）**：本机 HTTP 上的 JSON。`/health`、`/info`（UTC 服务器时间精确到毫秒、版本、构建类型、git commit、租约时长）、`/subscribed`、`/connected_apis`（GET）；`/subscribe`、`/resubscribe`、`/unsubscribe`（POST，body 为 `{strategy_name, demo, topics}`；`demo` 必填且必须等于配置里的 `demo`，否则在任何状态改变之前就回 400）。topic 按交易所 → 品种 → 行情类型嵌套，交易所和行情类型的拼写与 ring 路径一致：`{"Binance": {"BTC-USDT-SPOT": ["BBO", "TRADE"]}}`；响应用同样的树，每个类型一个值（`{"Ok": path}` / `{"Err": reason}`，path 是该策略自己的 ring）；`/subscribed` 只列出行情服务当前发布的 topic，和请求的 `topics` 同样拼写。在 Rust 里，请求和 `/subscribed` 是 `HashSet<Topic>`，响应是 `HashMap<Topic, SubscriptionResult>`（`SubscriptionResult = Result<PathBuf, String>`）；嵌套由 `provider_api.rs` 里的 serde adapter `topic_set` / `topic_map` 完成，模块文档里有完整示例。`/resubscribe` 替换该策略的整个集合。`/connected_apis` 按交易所返回 connector 调用的交易所 API（`[{description, api, doc}]`），方便以后的生产 agent 跟踪交易所 changelog；每个 connector 在 `ExchangeConnector::CONNECTED_APIS` 里硬编码它们，开始或停止调用某个 API 时手动修改。
- **服务端（`src/server/`）**：`http` 用 axum。`Coordinator` 在一把 `tokio::sync::Mutex` 后面，请求被串行化，去重不需要更细的锁。它拥有 `SubscriptionRegistry`，一张 `HashMap<策略名, Holding>` 记录每个策略持有的 topic 和租约到期时间，策略没有 topic 时整条删除。每个请求都会续期该策略的租约（`lease_duration`，默认 30 秒）；每秒扫描一次，清掉过期的策略，并通知 worker 不再给它发布。四种请求（subscribe、resubscribe、unsubscribe、租约过期）都只是算出该策略的目标集合，再交给 router 把它从已持有的集合移到目标集合；新增 topic 失败就不计入持有，已持有的 topic 即使被重新启动的 worker 拒绝也保留，下次请求会再发。行情服务在整个生命周期内只提供一种环境，所以 topic 只用 `Topic` 作键：每个 worker 都在这种环境下启动，每个请求的 `demo` 都必须与之一致。`/subscribe` 和 `/unsubscribe` 到达时以 info 级别记录策略和它的 topic；`/resubscribe` 请求的集合与该策略已持有的相同（忽略顺序和重复）时不记日志，否则以 warn 记录增加和去掉的 topic。`exchanges::ExchangeRouter` 维护 `HashMap<Exchange, WorkerHandle>`，只有一个方法 `set_topics(策略, 已持有, 目标)`：按交易所分组后逐个交易所处理（控制面，顺序执行），worker 在运行且该交易所的部分没变就跳过；worker 没在运行而目标非空就启动一个新的，并把该交易所的整个目标发给它（停止的 worker 带走了策略的 ring，所以要整个重发）；合并各 worker 返回的 `HashMap<Topic, String>` 失败原因；ring 路径由根目录、策略名和 `Topic` 推导。
- **交易所 worker（`src/exchanges/`）**：bcast 的 `Writer` 是 `!Send`，所以每个交易所在自己的线程上运行一个 current-thread tokio runtime。这个线程拥有该交易所的 `ExchangeConnector` 和全部 `MarketDataWriter`，从而保证每个 ring 只有一个写者。worker 按策略记录状态（`HashMap<策略名, StrategyRings>`，每个 `StrategyRings` 是该策略的 topic 和它的各个 ring 的 writer）：每条消息只序列化一次（`SerializedMarketData`），再依次写进每个订阅了它的策略的 ring。worker 只有一条命令 `SetTopics { 策略名, topics }`：`topics` 是该策略在本交易所的完整集合，worker 和自己持有的比一次差，打开新增 topic 的 ring、去掉减少的 topic，对每个失败的 topic 返回原因；同一个集合发两次不改变任何东西。router 按交易所分组，worker 收到别的交易所的 topic 说明代码有 bug，所以直接 `assert` panic，provider 的 panic hook 让整个进程退出。交易所侧的订阅仍然去重：某个 topic 第一次有策略要时才向交易所订阅，最后一个策略不要了才退订（`ExchangeConnector` 只接收 `HashSet<Topic>`）。策略退订或租约过期时，它不再用到的 ring 立即关闭（文件保留），策略的最后一个 topic 走后就从 worker 里移除。订阅只在 ring 文件创建之后才返回，所以推导出的路径立即可读。worker 按需启动：某个交易所的第一个 topic 会启动它的 worker，router 在 worker 线程上用该交易所 connector 的 `new(demo, ...)` 构建 connector；`new` 注入生产依赖但不建立任何连接（connector 自己选择交易所的 demo 或实盘域名）；交易所连接在 `subscribe` 里建立，并由它报告失败。`ExchangeConnector` 没有构造函数，所以它在 connector 的泛型依赖上实现，测试用 mock 驱动同样的 trait 方法。只有启动线程或 runtime 失败才会导致 worker 启动失败（这一批被拒绝，下一次订阅会重试）；停止的 worker 会被替换。worker 在最后一个策略离开后自行退出，关闭命令 channel，所以 router 不需要维护剩余 topic 计数。关闭时 worker 调用 `ExchangeConnector::disconnect` 优雅地关闭交易所连接。添加交易所：加一个 `Exchange` 变体、一个 connector 模块，并在 `router::spawn_exchange_worker` 和 `exchanges::connected_apis` 里各加一个分支（两个 match 都是穷尽的，编译器会强制）。`synthetic.rs` 是临时的，之后会删除。
- **传输（`layline::shared_memory`）**：`bcast::RingBuffer` 建在 `memmap2` 上。每个策略只读自己的 ring，里面只有它订阅的 topic；策略使用 `MarketDataReader`，只有交易所 worker 会创建 `MarketDataWriter`，所以每个 ring 只有一个写者。
  - **文件格式**：`ring_format` 定义文件长度和两者共用的元数据区（magic、`FORMAT_VERSION`、行情类型），模块文档里有整个文件布局的 ASCII 图。`MarketDataWriter::open` 接收根目录、策略名和 `RingKey`，自己推导路径；它只重新接上元数据匹配的 ring，否则重置；debug 构建下拒绝发布不属于自己 `RingKey` 的数据。reader 在 `into_reader` 之前检查元数据（`into_reader` 会一直空转等 writer 把 ring 标为就绪，没被 writer 初始化过的文件会让它永远卡住），拒绝不匹配的 ring。故意不用 `bcast::mmap::MappedWriter::new`，因为它会删除文件。
  - **读取**：`MarketDataReader` 对每个不同的 ring 路径只打开一次（一个策略在同一个 ring 里可能订阅了多个币种），轮流轮询这些 ring，把每条 `MarketData` 连同接收时间交给调用方的闭包。
  - **溢出**：遇到 `Overrun` 时调用 `reader.reset()` 跳到最新数据。一个策略的同一个 ring 里有它订阅的多个币种，其中一个爆量绕过一圈，会丢掉这个 ring 里所有币种的积压；别的策略的 ring 不受影响。
  - **读错误**：除 `Overrun` 外，bcast 只会返回 `InsufficientBufferSize`（消息比 `MAX_PAYLOAD_LENGTH` 大），这只可能是写端或格式的 bug，所以 `poll` 返回错误，和 rkyv 反序列化失败一样让策略退出。写端的 `SerializedMarketData::new` 不返回 `Result`：`Bbo`/`Trade` 序列化不会失败，失败就 panic。
  - **容量 8 MiB**：来自实测。2026-11-02 一个普通交易时段的 5 分钟里，Binance 永续 BTC、ETH 的 BBO 合计平均每秒约 1400 条，单个 1 秒峰值约 3000 条；现货 trade 单个 1 秒峰值约 1000 条。64 KiB 在永续 BBO ring 达到峰值时只够读线程停顿约 0.1 秒，8 MiB 可以撑十几秒。每个策略在 Binance、OKX 各最多 4 个 ring，即每个策略最多占 64 MiB 的 `/dev/shm`，页面在第一次写到时才分配。
- **序列化**：消息用 `rkyv` 编码，在 `from_bytes` 之前拷进一个 16 字节对齐、512 字节的栈上缓冲区，所以任何消息类型序列化后都不能超过 512 字节。修改 `Bbo` 或 `Trade` 会改变线上格式。目前还没部署过，开发期间 `FORMAT_VERSION` 保持为 1；第一次部署之后才递增。
- **时间戳**：`Bbo` 和 `Trade` 带有 `LatencyMetric`，时间都来自 `get_current_timestamp_nanoseconds()`。connector 读到交易所消息后、解析之前，立即通过 `LatencyMetric::received` 设置 `provider_receive_time_nanoseconds`。`SerializedMarketData::new` 在序列化之前覆盖 `provider_write_time_nanoseconds`，所以序列化和写进各个策略 ring 的拷贝都算作传输时间。策略读取时打上自己的接收时间；比较时钟要求同一台机器、同一个时钟源。`exchange_time_nanoseconds` 是交易所的时间戳，不在 `LatencyMetric` 里。
- **交易所 websocket（`exchanges/websocket/`、`exchanges/binance/`）**：`websocket/` 与交易所无关。`client.rs` 是接缝：一个 `WebSocketClient` trait，每个 client 一条连接（生产用 tungstenite，测试用 mock）。`WebSocketConnection<Client>` 永久持有一个 client，并加上心跳、保活和关闭逻辑：`next_message` 只交出 Text/Binary `Message`，连接断开后返回错误；它显式应答 Ping 和 Close，按 `Heartbeat` 发 ping、超时放弃，用 tokio 的绝对时刻记录，因此是 cancel-safe 的。`Heartbeat` 还带有 `connect_timeout`（卡住的握手不会拖住控制面）和 `Keepalive`：Binance 用 `PingFrame`，OKX 这类在应用层文本里保活的交易所用 `Text { ping, pong }`。`endpoint_set.rs` 提供 `EndpointSet<COUNT, Endpoint, Client>`/`EndpointState`：每个 endpoint 一条连接，加上它按交易所键记录的 topic 和恢复计划，方法有 `record_topics`、`forget_topics`、`schedule_restore`（指数退避）、`schedule_immediate_restore` 和 `due_endpoints`；下一个交易所复用它，而不是照抄 Binance 的记账逻辑。`venue_stream::endpoint_for_topic` 把现货映射到 SBE（`@bestBidAsk`、`@trade`），把永续映射到 JSON 合约 `/public`（`@bookTicker`、`@trade`），因为 Binance 只给现货提供 SBE。SBE 的 `bestBidAsk` 在高负载时可能丢弃过时的更新（auto-culling），JSON 的 `bookTicker` 不会；它到达得并不更早，但解码便宜约 4 倍，而 BBO 本来就只用最新值。Binance 对未知的 stream 名静默接受，所以这个映射必须有测试覆盖。`BinanceConnector` 每个 endpoint 持有一个 `WebSocketConnection`，以 stream 名为键（`venue_stream::stream_name`，如 `btcusdt@bookTicker`）。`endpoint.rs` 只存硬编码的 API 事实（URL、文档、`CONNECTED_APIS`）；topic 到 stream 的映射在 `venue_stream.rs`，直到有 InstrumentManager 负责交易所的拼写。endpoint 在第一个 stream 时连接、最后一个 stream 退订时关闭；每一批对每个 endpoint 发一个 SUBSCRIBE 或 UNSUBSCRIBE，并等待它的 `{"result":null,"id":N}`（10 秒），期间到达的事件先排队；请求失败则整批失败并回滚；订阅时连不上 endpoint（握手被拒、超时、DNS 失败等）则推送到手机，并以 `ExitReason::ExchangeUnreachable` 为载荷 panic，整个 provider 退出。已经连上过的连接丢失或请求失败时，在 `next_event` 内部重连并重新订阅所有 stream，先立即重试，然后从 1 秒开始翻倍退避到 60 秒；连续第 5 次失败时推送到手机。`message.rs` 是唯一的帧分类器：`classify_text_frame` 返回 `Response`、`Event` 或 `ServerShutdown`，`handle_frame` 据此把数据入队、应答请求或强制立即重连。事件用手写的单遍扫描器解析 Binance 的紧凑布局（release 下每帧约 150–200 ns，serde_json 约 450 ns），扫描器不认识的格式回退到 serde_json；合约的 `bookTicker` 和 `trade` 的 `T` 以毫秒为单位，`X: MARKET` 以外的成交被跳过。`sbe.rs` 不分配内存地解码现货 SBE 的 `bestBidAsk`（template 10001）和 trade（10000，每笔成交一个 `Trade`）帧；交易所时间以微秒为单位。每条消息的路径除了交易所的帧本身不做任何分配：endpoint 放在按 `BinanceEndpoint::index` 索引的数组里，`next_event` 用固定的 `select!` 在它们之上等待，SBE 的 stream 名在栈上构造。未知或无法解析的帧记日志后丢弃，从不致命。router、worker 和集成测试用 OKX，因为它们会启动生产的 Binance connector。
- **配置、API Key 和告警（`config.rs`、`phanes_client.rs`、`alert.rs`、`exit_reason.rs`；`layline::bark`、`layline::secrets`、`layline::gnosis`）**：和 Phanes 一样，所有配置来自一个 TOML 文件（权限 600），不读环境变量：`port`、`demo`、`[phanes_client]`（`url`、`client_gnosis_private_key`、`phanes_gnosis_public_key`，两个 key 都直接写 base64，解析时就解码；自己的公钥不用配置，Noise 由私钥推出）和 `[bark]`（见 `deploy/market_data_provider/market_data_provider.example.toml`）。`layline::secrets` 强制配置文件和 Phanes 密钥的权限为 600；配置经 `read_secret_toml` 解析，出错时只报 toml 的错误信息、key 路径和行号，不引用原文（原文可能含 Bark 凭据）。`MarketDataProviderConfig::load` 只解析和打印配置：`[phanes_client]` 总是必填，其中的密钥在解析时解码，坏的密钥在这里就拒绝启动。`server::run` 监听 `127.0.0.1:<port>`，以 `DEFAULT_ROOT_DIRECTORY` 和默认 30 秒租约调用 `serve`；测试直接调用 `serve`，自己传入 listener、ring 目录和租约时长。`serve` 先构造 `PhanesClient` 和 `Notifier`（`[bark]` 只有 release 构建需要，因为 `layline::bark::Notifier` 在 release 构建中经 Bark 推送，在 debug 构建中只打日志，缺了就在这里拒绝启动），再把它们作为 `ConnectorContext` 交给 router，router 再传给每个 connector 的 `new`。只有需要 key 的 endpoint（Binance SBE）才向 Phanes Gnosis 请求，每个 connector 一次，经 `fetch_gnosis_or_panic::<T>(GnosisSource, SendAlert, demo)`：`T` 是 `layline::gnosis` 里的 key 类型，它决定 gnosis id（`Gnosis::gnosis_id(demo)`）；Phanes 发来的 gnosis 直接按 `T` 解析（字段不符时报错只列字段名，不引用值）。Binance connector 只缓存 SBE key（`BinanceSbeApiKey`，gnosis id `binance_sbe_{real,demo}`）。取不到或解析失败时把 gnosis id 推送到手机，并以 `ExitReason::GnosisUnavailable` 为载荷 panic。这类"推送后退出"统一走 `alert::alert_and_panic`。退出码在 `ExitReason` 里从 1 递增：1 取不到 gnosis（API Key），2 其他致命错误（配置错误、端口被占），3 其他 panic，4 订阅时连不上交易所；二进制（`src/bin/market_data_provider.rs`）的 panic hook 在任何线程 panic 时 flush 日志，并以载荷对应的退出码退出。`SendAlert` 是本 crate 在 `Notifier` 上实现的尽力而为的告警：推送失败只记日志，不返回错误。
- **不依赖交易所、Phanes 和墙钟的测试**：`BinanceConnector<WebSocket, KeySource, Alerter, TimeSource>` 的泛型参数默认是生产类型；`new` 接收每个 endpoint 一个 `create_websocket` 闭包，测试通过 `BinanceFixture` 构建它，每个 endpoint 一个 `websocket::tests::MockVenue`（client 打开的每条连接都是一对由测试驱动的 channel，记录 URL 和 header，可以拒绝或忽略 Close，`respond_with` 自动应答请求；`BinanceFixture` 确认每一个请求），以及 `phanes_client::tests::MockApiKeySource`（按 key id 发放或拒绝，记录请求，可以离线；不涉及 Gnosis）、`alert::tests::RecordingAlert` 和 `utils::tests::MockClock`。`PhanesClient` 本身通过 `PhanesFixture` 测试，它的 mock `GnosisHttp` 用 `layline::gnosis::Responder`（协议真正的服务端那一半）应答。只给测试用的代码放在各模块的 `mod tests` 里；跨 crate 共用的 fixture 在 `layline::testing`（`test_instrument`、`test_topic`、`test_subscription`、`test_bbo`、`test_trade`、`test_keypair`；统一带 `test_` 前缀，测试模块里的同名本地 helper 不会和它们冲突，可以直接 import）。`utils::Clock`（`RealClock`，测试里用 `MockClock`）用于墙钟时间戳，如 `provider_receive_time_nanoseconds` 和 Gnosis 请求时间；定时器用 tokio 时间，测试用 `#[tokio::test(start_paused = true)]`（dev-dependency feature `test-util`）暂停时间，逐步推进到每个截止时刻之前和之后。只有 `websocket/client.rs` 测试真实的本地 socket；`live_futures_endpoints_deliver_bbo_and_trades` 标了 `#[ignore]`，会连接 Binance 的实盘和 demo。

## 运行与基准测试

```bash
cargo run --bin market_data_provider -- --config market_data_provider.toml   # 复制 deploy/market_data_provider/market_data_provider.example.toml，chmod 600
cargo test -p market_data_provider            # 单元测试 + tests/subscription.rs 端到端测试
cargo bench -p market_data_provider                                     # criterion 延迟基准
cargo bench -p market_data_provider -- --save-baseline before           # 之后用 --baseline before 对比
cargo test -p market_data_provider --bench latency                      # 每个 bench 只跑一次，做冒烟测试
```

启动 `market_data_provider --config <文件>`（默认 `market_data_provider.toml`）后，它创建 `/dev/shm/market_data_provider/`（`DEFAULT_ROOT_DIRECTORY`），在配置的 `127.0.0.1:<port>` 上提供 HTTP；策略在自己的 `strategy.toml` 里写 `provider_address`。地址被占用或配置无效时拒绝启动。在有策略订阅之前，不会启动任何交易所 worker。`curl localhost:6666/subscribed` 列出行情服务当前发布的 topic。

`crates/market_data_provider/benches/latency.rs`（criterion）自底向上测量数据路径：`codec`（rkyv 序列化，以及 reader 的拷贝加反序列化）、`publish`（`MarketDataWriter::publish` 写入 `/dev/shm` 里的 ring）、`poll_fan_out`（`MarketDataReader::poll` 读 1/8/64 个 topic，分别落在 1/4/4 个 ring 上，空闲和其中一个活跃两种情况）、`cross_thread_latency`（两个线程之间单向写到读的延迟，ping-pong 方式避免排队，按 `LatencyMetric` 的口径测量）。不对交易所 worker 做基准，因为合成行情每 10 ms 才一条。WSL2 上不绑核得到的数字只用于版本之间对比，不代表生产环境的绝对延迟；criterion 报告的是均值，不是尾部分位数。
